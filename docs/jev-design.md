# Jevによる候補評価・順位付け 拡張仕様書

作成日：2026-10-11（JST） / 状態：計画案。実装・実API検証なし。

追加要件により、Jevに類似するAPI・公開モデルも比較対象とする。[判断用AIの比較・共通仕様](decision-ai-comparison.md)を参照。本書の候補評価・採用原則は共通仕様へ引き継ぎ、TypeSafe固有の形式は専用アダプターに閉じ込める。

## 1. 結論と適用範囲

TypeSafe AIのJevを、CPE/PURLの取得済み候補を評価する補助モデルとして導入する設計は可能。既存の4社による候補生成と、Jevによる候補評価を分離する。公開API仕様を前提とした実現性判断であり、アクセス権、実データでの精度、運用条件は実装前の検証事項とする。

本書は[基本設計](design.md)の拡張計画である。初期導入はサーバー設定で有効化する内部評価機能とし、既存のHTTP入力・結果契約とDDLを変更しない。クライアントがJevを個別指定するAPIや確率を公開するAPIは将来の別契約として扱う。本書の設定名・内部データ名は提案であり、現在利用できない。

## 2. 公式仕様から確認した前提

2026-10-11に以下の公式資料を確認した。

- [紹介記事](https://typesafe.ai/blog/introducing-system-one-models-and-jev)：Jevは自由な文字列生成を行わず、事前に定義した構造で判断を返すモデル。記事はearly accessと説明している。
- [Introduction](https://docs.typesafe.ai/introduction)：状態と型付き質問を渡して、Choice・Score・Noulの結果を取得できる。
- [Quick start](https://docs.typesafe.ai/introduction/quickstart)：`POST https://api.typesafe.ai/v1/systemone`、Bearer認証、`state`・`model`・`questions`を使うHTTPインターフェースが示されている。
- [Primitives](https://docs.typesafe.ai/primitives)：Choiceは選択肢、Scoreは順序付き段階、Noulは二値の確率を扱う。各質問は同じ状態に対して独立に評価される。
- [Confidence](https://docs.typesafe.ai/confidence)：Choice/Scoreのconfidenceは確率分布から計算した指標。Noulには別のconfidenceがない。

型の保証と、意味・製品同一性の正しさは別である。公式の速度・価格・校正性能の主張を、このアプリの性能保証に転用しない。モデルの確率は入力との対応に関する補助情報であり、外部登録の証明ではない。

## 3. モードと役割

| モード案 | 動作 | 用途 |
|---|---|---|
| off | 既存の処理のみ | 初期既定値 |
| shadow | 既存判定を固定して同じ候補をJevで評価。正式判定へ反映しない | 精度・費用・遅延の比較 |
| assist | Jev評価を表示順位と要確認理由へ反映。最終採用は既存ルール | 評価合格後の運用 |

shadowの評価失敗は正式ジョブの状態を変更しない。shadow評価はジョブ実行期限内に終え、内部監査情報も終端移行前に保存する。期限不足時はskippedとし、終端ジョブへ後から追記しない。assistでは失敗時の方針を事前設定し、既存評価へ戻す場合はフォールバックを記録する。必須評価に設定した場合は対象別エラーとして既存partial/failed規則へ渡す。

Jevには別名、新しいCPE/PURL文字列、バージョン、説明文章の生成を求めない。Jevのみの運用では、入力識別子・NVD検索・決定的な規則で得られる候補の評価に範囲を限定し、候補再現率低下を別途測定する。初期版ではこの単独モードを提供しない。

## 4. 処理フロー

1. 既存パイプラインで入力を正規化し、必要なら4社のうち設定した1社で候補を生成する。
2. NVD/OSVを照会し、構文、取得状態、同一性の支持・矛盾情報を規則で整理する。
3. 対象ごとに最大5候補をJev評価用の状態へ変換する。取得結果の原文と、アプリの照合結果を区別する。
4. 候補ごとのScoreで入力との適合度を評価する。Choiceで全候補と`none`・`insufficient`から最も適合するものを選ばせる。
5. 応答をローカル検証し、候補IDへの対応を復元する。Scoreの降順で表示し、同点は元の順位・候補IDで安定化する。
6. ChoiceとScoreの首位が異なる場合は競合として要確認にする。AIの高評価で規則上の矛盾を解除しない。
7. 最終判定、根拠、モデル使用情報を既存のサービス層で保存する。

候補0件ではJevを呼ばず、既存の照会状態を返す。CPEとPURLは別の評価単位とし、一方の選択を他方の確認根拠にしない。候補数の上限で除外した候補数と、外部検索の打ち切りを別々に記録する。

数万件以上の辞書は全件をChoiceへ渡さず、検索・規則で作業候補集合を作ってから最大5件を評価する。[共通仕様の大規模辞書設計](decision-ai-comparison.md#8-数万件以上の辞書から候補を探す設計)に検索再現率、削減時の取りこぼし、追加探索と未解決の扱いを定める。

## 5. 質問・入力仕様

状態には対象種別、入力名、ベンダーの役割、明示されたバージョン・エコシステム、候補値、参照ID、支持フィールド、矛盾フィールド、不足情報を含める。未取得情報は不明と明記する。

| 質問 | 型 | 定義 |
|---|---|---|
| 候補別の適合度 | Score | 0=明確な矛盾、1=情報不足、2=もっともらしいが曖昧、3=独立した識別情報が整合 |
| 最適候補 | Choice | 候補ごとの不透明な選択キー、none、insufficient |
| ベンダー役割の曖昧さ（任意） | Noul | 入力のベンダーが開発元か配布元か区別できないか |

Scoreは小数値も受け取り、整数に丸めて採用判定しない。Noulは曖昧さの補助フラグに限り、単独で候補の正否を決定しない。欠損バージョンなど機械判定できる条件はGoの規則で扱う。

質問IDだけに意味を持たせず、instructionsに対象候補と状態の参照位置を記載する。候補評価と候補選択は独立した質問であり、同一呼出内でScoreをChoiceが参照するとは想定しない。

外部説明文・SBOM文字列はデータ領域に置く。命令文やURLを実行しない。Jevから追加のネットワーク取得やコマンド実行を行わせない。

## 6. 内部契約と実装境界（予定）

既存の`AIProvider.Propose/Rank`とは別に`CandidateEvaluator.Evaluate(ctx, request)`を設ける。JevにProposeを実装させない。生成・評価の能力を分け、将来の同種モデルも交換可能にする。

- request：component、target、候補・根拠要約、質問版、候補選択キーと内部IDの対応。
- response：候補別scoreと分布、Choice選択・分布、任意Noul、応答モデルID、使用量、評価状態。
- 実装配置案：`internal/evaluate`に共通契約、`internal/provider/typesafe`にHTTP変換、`internal/decision`に採用規則。
- Goの`net/http`を使用し、Python SDKへの依存を設けない。HTTP APIとCLIは同じサービス設定・評価処理を使用する。

応答のサイズ、質問ID、型、選択肢集合、有限数値、値域、確率分布の合計（許容誤差を明示）を検証する。未知・欠損キー、無効な候補対応、モデルの不一致は評価エラーにする。Jevの型保証があっても通信応答の検証を省略しない。不正応答に文章修復依頼は行わない。

## 7. 採用・確率の扱い

Jevはverification.status、checked_at、complete、evidence_idsを変更できない。NVD登録確認と入力への適合、OSV記録一致とパッケージ実在は従来どおり区別する。

自動採用には既存の確認済み・独立した識別情報の一致・競合なしの条件を必須とする。名前・ベンダーだけ、未知バージョン、検索不完了、根拠なしはJevの高確率で自動採用へ昇格しない。採用候補は元の候補集合に存在しなければならない。

confidenceを「正解率」と表示しない。Choiceの確率は渡した選択肢集合に依存するため、異なる候補集合間で直接比較しない。none/insufficientが首位、候補間の競合、校正後の基準未達ではreview_requiredとする。候補のないケースは既存のunresolvedを維持する。

初期導入では確率による採用範囲拡大を無効にする。閾値は評価セットで決め、質問版・モデル版・候補数別に管理する。モデルの自己申告値による自動採用を禁止する既存原則を変更しない。

## 8. 設定・外部I/O

サーバー設定案：evaluation_mode、evaluator_provider、evaluator_model、evaluation_required、timeout、max_attempts、max_request_bytes、max_response_bytes、call_budget、fallback_policy。利用者のリクエストでは任意URL・質問本文・秘密鍵を指定させない。

秘密鍵は`TYPESAFE_API_KEY`から取得し、モデルIDは必須設定とする。最新モデルの別名をコードに固定しない。別名を使用した場合は要求モデルと応答の実モデルを保存する。

初期運用案はタイムアウト5秒、最大2試行（初回を含む）、入力64 KiB、応答256 KiB、1対象につき評価1回（再試行を除く）。実際の提供API上限との整合を実装前に確認し、上限超過を黙って切り詰めない。最大1,000コンポーネント・2対象なら最大2,000評価となるため、ジョブ単位の呼出予算も必須にする。

contextでキャンセルを伝播する。429/一時的5xxのみ上限付きバックオフ・ジッター・Retry-After対応とし、認証エラーや恒久的入力エラーは再試行しない。外部エラー本文をそのままログ・利用者応答に出さない。

フォールバックはoff・existing_rankerから明示設定し、許可されていない他社へ転送しない。shadowでも費用と外部送信は発生するため、運用者が明示的に有効化する。全SBOM、社内URL、不要なパスを送信せず、外部送信ポリシーを共通適用する。

## 9. 保存・既存API/DBとの関係

`options.provider/model`とDBのprovider/modelは既存4社による生成設定の意味を維持する。typesafeを生成プロバイダー列へ追加しない。`GET /v1/providers`も引き続き生成プロバイダーの一覧とする。

評価情報は既存のrun_metadata JSONBに内部監査情報として保存する計画とする。項目案は評価モード、要求/応答モデル、質問版、評価状態、候補集合ハッシュ、入力要約ハッシュ、候補別分布、選択結果、所要時間、試行数、使用量、フォールバック理由。shadowの情報を正式な候補・外部根拠へ混ぜない。

公開run_metadataへの出力は現在のOpenAPIが許容する項目だけとし、内部の詳細を無条件に返さない。候補別確率などを利用者に公開する段階では、OpenAPI・API設計・DB設計を同時に更新し契約検証する。現段階の新仕様は内部計画に限る。

費用が取得・算出できない場合は金額を保存しない。根拠スナップショットと評価ログを区別し、保存期間と所有者境界は既存ジョブに合わせる。評価キャッシュを導入する場合は入力・候補・モデル・質問版をキーに含め、モデル版が特定できない別名で版をまたいだ再利用をしない。

## 10. 評価・受け入れ条件

既存4社の評価、Jev補助評価、規則だけの結果を同じ候補・外部データスナップショットで比較する。生成品質と評価品質を分離し、候補集合内の正解選択率、none/insufficientの適切さ、誤採用数、要確認率、費用、評価単体/全体のp95遅延を測る。

評価データには同名異種、fork、開発元/配布元の違い、未知バージョン、非推奨CPE、OSV空応答、外部障害、候補不在、悪意ある説明文を含める。製品系列で学習・調整用と評価用を分離する。確率は信頼度曲線・Brier scoreなどで検証し、高confidenceの誤りも点検する。

受け入れ条件：

1. 不正応答、タイムアウト、キャンセル、429、認証失敗をネットワーク不要のfixtureで再現できる。
2. Jevが確認状態・根拠・未知バージョンを捏造または上書きしない。
3. none/insufficient、同点、Choice/Score競合を保守的に処理する。
4. shadow有無で正式結果・正式ジョブ状態が変わらない。
5. assistで既存の自動採用精度99%以上という暫定目標を維持し、件数・誤採用数・カバレッジを併記する。少数標本では達成を断言しない。
6. 秘密鍵・機密原文をログや他所有者へ露出させない。
7. ライブ検証は明示設定されたAPIキーと匿名化データに限定し、通常CIから分離する。

2. 共通評価契約と質問・fixtureを作り、Go HTTPアダプターを契約テストする。
3. 匿名化評価セットでshadow比較を行い、速度・費用・校正を測定する。
4. 結果が受け入れ条件を満たす範囲でassistを有効化する。問題時はサーバー設定でoffへ戻せるようにする。
5. 必要性が確認できた段階で利用者向け評価指定・確率表示のAPI拡張を別途設計する。

本作業では仕様書のみ作成する。接続、キー取得、SDK/スキル導入、コード実装、API/DDL変更、デプロイは行わない。提供側の公開仕様変更と、Jevのドメイン精度は残る制約であり、導入を保証するものではない。
